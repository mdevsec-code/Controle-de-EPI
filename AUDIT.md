## 0. Resumo executivo

O repositório **não é um app legado em JavaScript à espera de migração**. Na verdade, ele contém duas coisas:

1. **O legado (`legado/`)**: um protótipo navegável em **HTML + JavaScript puro** (`legado/index.html`, ~1.200 linhas, tudo com dados fictícios), 11 screenshots do produto, uma landing page de apresentação (`index_final.html`) e um scaffold React vazio (boilerplate do Vite). Ele define **o comportamento e a identidade visual de referência** (ENGENOVA, laranja, fluxo de entrega em 9 telas).
2. **A reescrita em andamento (`apps/`, `packages/`, `database/`)**: um monorepo **pnpm + Turborepo** que já usa **TypeScript strict**, React 19 + Vite, Express 5, Zod, Prisma 7 e PostgreSQL. Ou seja, a stack-alvo da Seção 5 do pedido **já foi adotada**.

Estado real da reescrita:

| Área                                                                                | Situação                                                                                                                    |
| ----------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| API — autenticação (JWT + refresh rotativo + RBAC)                                  | Implementada, com falhas pontuais (ver A-04, A-05)                                                                          |
| API — empresas, unidades, setores, cargos, colaboradores, EPIs, CAs                 | Implementadas (CRUD sem exclusão)                                                                                           |
| API — **estoque, entregas, devoluções, assinatura, QR Code, auditoria, relatórios** | **Não existem**                                                                                                             |
| Banco                                                                               | Schema Prisma completo, **sem nenhuma migration**                                                                           |
| Web                                                                                 | 9 telas do fluxo de entrega, **100% com dados fictícios**: nenhuma chamada à API, sem login funcional e sem guarda de rotas |
| Testes                                                                              | 16 testes unitários na API (todos passam); zero no web                                                                      |
| Build / Lint                                                                        | Passam                                                                                                                      |

**Os 4 problemas críticos:**

- **C-01:** o fluxo de entrega exibe "Entrega registrada com sucesso", mas não grava nada.
- **C-02:** não há migrations versionadas.
- **C-03:** o modelo de estoque permite saldo negativo e não tem controle de concorrência.
- **C-04:** a entrega não registra o CA nem uma assinatura com valor de evidência, o que é exigido pela NR-6.

**Achado de alto impacto em produto:** a reescrita trocou a identidade **ENGENOVA** (laranja `#EE5A24`, logo, Sora) por uma marca genérica "EPI Manager" em azul (A-01).

**Consequência para o plano:** a "migração JS → TS" (Fase 3) se resume a **portar o comportamento do protótipo** e **endurecer os contratos de tipo** (DTOs compartilhados, eliminar `any` implícito de `req.body`). O grosso do trabalho está em **domínio (entrega/estoque/assinatura), integração web↔API, segurança e testes**.

## 6. Dívida técnica (3.4) — funciona, mas está arquiteturalmente frágil

1. **Fluxo de entrega acoplado a mocks e à navegação.** Cada tela lê um `zustand` global e faz `<Navigate>` defensivo. Não existe um "rascunho de entrega" com regras (ex.: colaborador ativo, quantidade 1..50, EPI com CA válido). A regra "só ativo pode receber" está **no componente** (`employee-found-page.tsx:61`). Proposta: `features/deliveries/model` com funções puras de validação do rascunho (testáveis) e a mesma regra validada no backend.
2. **Composição de dependências espalhada.** Cada `*.routes.ts` instancia seus repositórios e serviços (`PrismaEpiItemRepository` é criado 2×, `PrismaBusinessUnitRepository` 2×). Funciona, mas dificulta transações entre módulos. Entrega e estoque precisarão compartilhar a mesma transação (`prisma.$transaction(tx => …)`). Proposta: repositórios aceitarem um `tx` opcional, ou o caso de uso de entrega usar o Prisma transacional diretamente. **Não** introduzir container de DI.
3. **Classes `Service` monolíticas por entidade** (`EmployeeService` com create/update/block/unblock/terminate/list). Aceitável hoje. Para entrega e estoque, preferir casos de uso nomeados (`RegisterDelivery`, `ReturnEpi`, `AdjustStock`), como já é feito em `auth/`.
4. **Datas e números como `Date`/`number` crus no JSON.** `unitValue` Decimal → `Number` (perde precisão em valores grandes); datas sem padrão de timezone. Definir no contrato: ISO-8601 UTC e dinheiro em centavos (inteiro) ou string decimal.
5. **Paginação offset (`skip/take`) + `count`** em todas as listas. Suficiente para o porte esperado; registrar o limite (histórico de entregas deve ter filtro de data obrigatório e índice `(delivered_at)`).
6. **Status de colaborador sem máquina de estados.** `block`/`unblock`/`terminate` aceitam qualquer origem (é possível desbloquear um DESLIGADO). Regras de transição explícitas no domínio.
7. **`Delivery.latitude/longitude/deviceInfo`** existem no schema sem requisito correspondente. Coletar geolocalização é dado pessoal (LGPD): manter apenas se houver base legal; senão, remover.

## 11. Banco de dados

### 11.1 Schema atual (resumo)

```
Company 1─N BusinessUnit 1─N Department (auto-relação parent/children)
                         1─N Warehouse 1─N StockItem N─1 EpiItem
                         1─N Employee  N─1 Department, N─1 JobRole, N─1 Employee (supervisor)
User 0..1─1 Employee · User 1─N RefreshToken · User 1─N AuditLog · User 1─N StockMovement · User 1─N Delivery (deliveredBy)
```

## 13. Testes — situação e prioridade

**Situação:** 4 arquivos e 16 testes, todos unitários de serviço com repositórios simulados (`login`, `company`, `employee`, `epi-ca`). Eles têm valor real (cobrem regras de unicidade, referência cruzada e credenciais) e devem ser mantidos.

**Lacunas, em ordem de prioridade (Seção 32):**

1. **Estoque e entrega:** integração contra Postgres real, incluindo o **teste de concorrência** (N entregas paralelas com saldo 1 → exatamente 1 sucesso, saldo final 0, N−1 recebem `409 ESTOQUE_INSUFICIENTE`) e idempotência (mesma chave → uma entrega).
2. **Autenticação:** refresh com rotação, reuso de token revogado, logout, usuário inativo.
3. **Autorização:** matriz perfil × rota via supertest (cada rota de escrita retorna 403 para os perfis não permitidos), escopo por unidade (IDOR).
4. **Entrega (domínio):** colaborador não ativo, CA vencido, quantidade fora de 1..50, snapshot de CA, assinatura obrigatória.
5. **Assinatura:** hash calculado e verificável; entrega imutável após assinada.
6. **Web:** fluxo de entrega ponta a ponta com msw (incluindo erro de estoque insuficiente exibindo mensagem específica e o botão desabilitado durante o envio); guarda de rotas; interceptor de refresh.

## 14. Decisões

### 14.1 Decididas (2026-10-06)

| #   | Decisão                                                                                                                                                   |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Colaborador **não faz login nesta fase**: assina no aparelho do almoxarife, como no legado. Login próprio (matrícula + PIN) fica para uma fase posterior. |
| 2   | Perfis: **`ADMIN` e `ALMOXARIFADO`**. `COLABORADOR` entra junto com o login do colaborador. Os outros 5 perfis do schema saem.                            |
| 3   | **App web único** e responsivo, com layout e rotas por perfil; PWA depois. `apps/mobile-pwa` será removido.                                               |
| 4   | `legado/` será **enxugado**: ficam `index.html` + screenshots; o logo é extraído; scaffold, scripts e landing saem (permanecem no histórico git).         |

### 14.2 Em aberto

Os itens 1–4 abaixo foram decididos (ver 14.1); os itens 5–7 continuam em aberto.

1. **O colaborador faz login?** No legado e nas telas atuais, quem opera é o almoxarife; o colaborador **só assina no aparelho do almoxarife**. A Seção 10 descreve um fluxo próprio do colaborador. Opções:
   - (a) manter como no legado (sem login do colaborador; `COLABORADOR` é uma pessoa, não um usuário);
   - (b) colaborador com login próprio (matrícula + PIN) para consultar suas entregas e assinar;
   - (c) (a) agora e (b) depois.

   _Recomendação: (c)._

2. **Perfis:** reduzir os 7 perfis do schema para os 3 do pedido (`ADMIN`, `ALMOXARIFADO`, `COLABORADOR`), ou manter alguns (ex.: `TECNICO_SEGURANCA`, `CONSULTA`)? _Recomendação:_ `ADMIN`, `ALMOXARIFADO` e, se (b)/(c), `COLABORADOR`. Adicionar outros só quando houver um usuário real com necessidade distinta.
3. **Um app ou dois?** `apps/mobile-pwa` está vazio. _Recomendação:_ um único app web responsivo (rotas e layout por perfil) e, depois, torná-lo PWA. Remover `apps/mobile-pwa`.
4. **Pasta `legado/`:** manter só `index.html` + screenshots como referência e remover scaffold, scripts e a landing de 3,6 MB (após extrair o logo)? Tudo permanece no histórico git.
5. **Tamanho e lote:** os EPIs têm grade de tamanho (bota 38–44, luva P/M/G) no estoque? Há mais de um almoxarifado por unidade em uso real?
6. **Deploy:** web e API ficarão no mesmo domínio (ex.: proxy `/api`)? Isso define a política do cookie (M-15) e o `trust proxy` (A-10).
7. **Login por e-mail ou por usuário?** O legado mostra "Usuário" (`marcio.almox`); a API usa e-mail.
